# Choice-likelihood development cycle — 2026-09-14

Status: prospectively specified before new likelihood outputs. H1/H4 remains closed and inconclusive. This is a new surrogate, not a revised analysis claiming expected-correctness prediction.

Use exactly the archived warm parent and four H4 displacements, in the existing order, with the frozen 16 score / 32 development image panels. Original image hashes, scene audit, coordinates and candidate parity checks remain mandatory. No final test; no new text updates, responses or prompt search. Candidate hardware remains confounded.

Objective: average log probability of the correct label, normalized over valid label-token sequences under the fixed answer-only system prompt in choice_probe.py. No EOS appended; labels represent prefix events and must be token-prefix-free. One-token alternatives use their logits directly; multi-token alternatives use summed sequence log probabilities. Gold labels select the target only. Units: natural log probability per image, not accuracy or percentage points. FP32 model, math SDPA, no autocast or TF32. This differs deliberately from the old BF16 sampled policy. It removes response-sampling noise, not scene uncertainty or surrogate mismatch.

Run one parent forward panel, one score-panel gradient, and four child score/dev forward panels. Dot each actual displacement with the common gradient. Seal alignment, cosine, norm and direct score-set likelihood change before the corresponding dev evaluation. Retain per-image likelihoods, token IDs, timings and peak memory. No optimizer or generation API is invoked. Persist completed stages atomically; interruption during gradient calculation currently requires repeating that phase in a new output directory. Do not claim automatic resume.

Engineering acceptance: finite likelihoods/gradients, nonzero gradient norm, exact displacement norm validation, identical deterministic parent replay, forward/backward objective agreement to 1e-7, final parent restoration replay. Treat failure as an implementation/numerical issue; do not interpret rankings. CPU tests must validate gradient sign and directional finite differences, vocabulary-normalization cancellation, token-prefix ambiguity rejection and no target leakage.

Development decision (descriptive, not a paper hypothesis test): compare candidate ordering for alignment, direct lookahead, cosine and norm against dev likelihood changes. Report all four candidates and all six dependent pairs, including ties. Do not use a six-pair binomial significance test. Report paired per-scene dev changes and scene-cluster bootstrap intervals as exploratory panel sensitivity, not a population claim for this availability-selected sample. Do not tune the prompt or precision after inspecting ranking. An unresolved or discordant ranking does not authorize a sweep. Four candidates can reject an obviously unhelpful implementation but cannot establish predictive validity.

Numerical resolution must be assessed from repeated fixed-model evaluations. If candidate differences are near the observed numerical floor, report them as unresolved, not ties proving equivalence. The CPU finite-difference test alone does not certify VLM numerical sensitivity; compare gradient predictions with direct score-set changes as a necessary on-model check. No automatic larger step or horizon.

Cost decision: separately report shared parent forward cost, shared gradient cost, displacement load/dot cost, each score/dev forward cost, overall elapsed and GPU memory. Include tentative text updates when forecasting selection cost. No efficiency claim unless total selection plus training plus evaluation cost is measured. Direct lookahead is a serious alternative; it is not a gradient approximation.

Advance only to a separately locked selection study if the engineering checks pass, ranking generalizes descriptively, and the projected selection overhead fits the stated budget. Generated-answer improvement remains an independent requirement. No result here establishes that requirement.
