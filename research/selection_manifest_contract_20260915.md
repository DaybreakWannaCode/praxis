# Static selection manifest preparation

`selection_manifest.py` builds Alignment and Random batch memberships from a complete fixed score pool before independent outcomes are inspected. It requires a shared parent, scoring protocol, calibration split and likelihood objective; distinct candidate/prompt IDs; finite scores; and per-candidate receipt hashes. Extra fields, including outcomes, are rejected. Higher alignment wins even when every score is negative. Fixed hash ordering breaks ties and controls membership/order reproducibly.

The default proposal is 64 candidate batches, 32 selected batches and 32 prompts per batch. Seeds must be supplied explicitly; this does not freeze their choice. Alignment membership is static across training seeds. Random membership depends on seed and candidate identity, never alignment values. Every arm receives the same prompt count and a seed-defined batch order. Training must still generate fresh rollouts; no tentative child is adopted as a trained arm.

The saved manifest includes the canonical score-pool hash and cannot overwrite an existing path. Three local tests passed: negative-score ordering and input-order invariance; random membership unchanged by score reversal; and rejection of outcomes, mixed parents, repeated prompts and output overwrite. These are fixture tests; no real pool or selected dataset was generated.

Upstream must validate the actual score receipts, input/code identities and scene separation, then archive the exact score pool before using the manifest. Hash strings alone do not prove those conditions. Pool membership, seed choices, scoring objective, independent endpoint, compute allocation and storage remain to be frozen/authorized. This module does not launch runs or establish a selection benefit.

## Preserve scored batch membership during training

The original baseline configuration has `data.shuffle: true`, which randomly mixes individual prompts. Reusing it unchanged would destroy the candidate batches used for scoring. Selection manifests now retain explicit per-batch prompt IDs in addition to the flattened dataset order. The pre-initialization `validate_training_handoff` check requires that exact order, prompt-level shuffle disabled, matching rollout/actor batch sizes, one actor epoch, five fresh rollouts per prompt and one pass over the selected batches. Batch order is already randomized by the sealed seed-defined order; both selectors use the same rule.

Seven tests passed across manifest construction and handoff validation. Additional cases reject the original prompt-shuffle setting, reordered datasets, different optimizer minibatches and inconsistent flattened/batched membership. No existing baseline configuration or completed run was changed. This is a validator ready for the future launch path, not yet an integrated training launcher. Source text integrity, effective runtime optimizer counts and fresh-rollout provenance still need upstream/runtime checks. Preserving selected batches does not guarantee the original candidate score remains valid after later updates.

## Seed semantics: unresolved rollout policy

Read-only inspection of the original deployed source found that `data.seed` seeds the RandomSampler in `RayPPOTrainer._create_dataloader`. The original vLLM constructor does not explicitly pass an experiment seed, and the FSDP/vLLM sharding manager initializes its generation CUDA state with `gen_dp_rank + 1000`. Therefore a dataset-order seed is not evidence of an independently seeded rollout stream. Current manifest seeds explicitly control random-arm membership and both arms' batch order only; this is now also recorded in the manifest's `seed_scope` field.

Different batch orders can produce different optimization trajectories even with a shared initial random stream, so these observations do not prove the proposed runs would be identical. However, calling them independently seeded rollout replications would be unsupported. Before the multi-seed study, freeze whether replication randomizes data order alone or also explicit rollout/training RNG. If the latter, pass and archive that policy after parent restoration through the actual generation path, then verify it there. Changing only `data.seed`, or seeding before restoring checkpoint RNG, is insufficient evidence. Do not alter completed baseline or audit runs.

Inspected source locations: `verl/trainer/ray_trainer.py` (`_create_dataloader`), `verl/workers/rollout/vllm_rollout/vllm_rollout_spmd.py` (engine and SamplingParams construction), and `verl/workers/sharding_manager/fsdp_vllm.py` (generation RNG initialization). No worker or rollout code was modified in this source review.

### Per-call seed interface confirmed in source

Further inspection found `generate_sequences` invokes `update_sampling_params(**prompts.meta_info)` around the engine generation call. The context manager applies keys present on `SamplingParams`, then restores prior values on normal return. This is the existing interface to use for an explicit sampling seed, after verifying the installed SamplingParams seed field and observing actual repeated outputs. It does not establish end-to-end replay by itself.

Proposed policy for a future launcher: seal a seed schedule indexed by replication and update, pass the same schedule to both selector arms, and archive each effective seed with captured rollout inputs. Distinct replications use distinct schedules. Shared seeds across arms provide pairing, not identical completions on different prompts or models. Separately distinguish restored training RNG from rollout sampling seeds. Verify a repeated parent/batch/seed before scientific execution; a different seed is not guaranteed to change every sampled response.

The original context manager lacks a `finally` clause: a generation exception skips restoration of sampling settings. Future execution should fail the job and recreate the worker from its parent instead of retrying in a potentially altered live sampler. No original code was patched and no generation was launched during this inspection.

## Fresh warm-parent arm versus interrupted-run resume

The original `_load_checkpoint` restores both the actor and old dataloader state, and sets the driver global step from the parent directory name. Its training loop stops at an absolute `training_steps` cap. Thus reusing a step-16 parent's loader and a 32-step cap is not a valid way to train 32 fresh selected batches: it can restore the wrong dataset position and leave only 16 new updates. This source finding affects proposed selection launchers, not the completed ordinary baseline.

`selection_warm_start.install_selection_warm_start` provides an opt-in per-instance fresh-arm load entrypoint. It validates the sealed batch handoff, calls the original actor restore interface, leaves the newly constructed selected loader untouched, and starts the arm-local driver step at zero. The caller must supply a freshly constructed loader from the verified selected dataset; the helper does not certify loader provenance. It records a load-return receipt and refuses repeated invocation, including after a failed restore. It does not implement interrupted-arm resume, which must restore that arm's own dataloader and step.

Optimizer/scheduler counters retain the warm parent's history. For example, if all relevant parent counters are 16 and each batch makes one optimizer/scheduler step, arm step 32 has counter 48, not 32. Freeze those expectations from the actual update configuration and use the explicit checkpoint-binding schedule. Restored scheduler internals and new training-budget configuration also need validation; do not silently reset learning-rate history.

Five local tests passed across fresh-arm and batch-handoff tests. The new case supplies an unreadable old dataloader file, exercises original-loop cap semantics over four selected fixture batches, verifies all selected IDs are consumed, and checks only the original actor load interface is called once. This is fixture coverage, not an executed original-worker selection run. The helper is not installed into historical trainers, and no selected-data GPU run was launched.

### Scheduler continuation check

On September 15 a CPU-only check used the deployed original `get_constant_schedule_with_warmup` factory and actual step-16 `extra_state_world_size_1_rank_0.pt` scheduler state (file SHA-256 `e7cebcab07c9876b92358e8965f88775dab6f0287df7fec3809b916457354627`). The existing configuration has zero warmup and a constant 1e-6 learning rate. Tiny SGD parameter groups were initialized with the saved base/current rates, the scheduler state was restored, and 32 optimizer/scheduler calls advanced its epoch from 16 to 48 with every emitted rate exactly 1e-6. The check passed; no model, Adam state, rollout or GPU computation was involved. It verifies scheduler continuation arithmetic for this configuration, not actual training updates.

Source inspection of `FSDPWorker` confirmed the scheduler is constructed from `int(lr_warmup_ratio * training_steps)` and stepped once after each actor update call. Therefore the zero-warmup setting avoids a changed warmup boundary when the new arm budget is 32. Nonzero warmup or another schedule would require separate review: restoring LambdaLR state alone does not certify that a newly constructed schedule function matches its original closure. Keep this experiment's original zero-warmup constant schedule; the new driver counter does not justify resetting the worker scheduler.
